# PFC Tracker — ログイン不要版

食品・食事・PFC・カロリーを記録する日本語PWAです。**メールログインなしで、そのまま使えます。記録はブラウザ内に保存し、最初に端末を連携すればスマホ・PCで自動同期できます。**

公開URL: https://pfc-bay.vercel.app

## 使い方

1. ホームから「食品を記録」、または「食品」で食品を登録します。
2. 食品名と100gあたりのP/F/C・カロリーを登録します。出典情報は任意です。ブランド、出典種類、版・確認日、エネルギー根拠、ポーション換算の入力は不要です。
3. グラムで分量を指定し、朝食・昼食・夕食・間食に記録します。旧版で登録したポーションは引き続き利用できます。
4. ホーム・履歴で日付を選び、摂取量・目標・残量・超過・達成率を確認します。
5. 設定で適用日付き目標と、バックアップを管理します。

初期目標: P 107g / F 70g / C 335g / 2,400kcal。カロリー目標はPFCと独立しています。食品・重量変更時だけ栄養値を再計算し、食品マスター変更・削除や日時だけの編集では過去の栄養スナップショットを保持します。日付はAsia/Tokyoで集計します。

食品名には炊飯前後・生/加熱・皮の有無を明記してください（例: ご飯〈炊飯後〉）。重量が未登録のポーションに共通重量を仮定しません。公式データ・メーカー値は同梱せず、確認済みのラベル・一次資料から手動登録します。テスト内の食品は架空です。

## 保存場所とバックアップ

- 保存先は **この端末の、このブラウザのIndexedDB** です。同期を有効にした場合は、端末で暗号化した記録もSupabaseへ送ります。
- **最初の端末連携後、iPhoneとMacは自動同期します。** 未連携のブラウザは独立した保存先です。
- ブラウザのサイトデータ削除、端末変更、プライベートモードの終了等で記録を失うことがあります。定期的にバックアップしてください。
- 同じブラウザを使える人は記録を閲覧できます。共有端末ではOS・ブラウザ側のアクセス管理を利用してください。
- IndexedDBが利用できない・容量が足りない場合はエラーを表示します。保存に失敗した状態を成功扱いせず、メモリ保存へ切り替えて永続化を装うこともありません。

**書き出し:** iPhoneでは「設定 → ファイルに保存・共有」から「ファイルに保存」を選べます。対応しない環境では「バックアップを書き出す」でJSONをダウンロードします。ファイルをiCloud Drive等、自分で管理できる場所へ保管してください。食品・食事・目標・お気に入り・テンプレートが含まれます。ファイルは暗号化されません。

**復元・端末移動:** 移動先でもアプリを開き、「設定 → バックアップを読み込む」でファイルを選びます。形式・数値・重複ID・食品参照・日時を検証し、確認後に **移動先の現在の記録をすべて置き換えます**。マージ・競合解決は行いません。必要なら先に移動先も書き出してください。非対応バージョンや壊れたファイルは拒否し、現在の記録を変更しません。読み込み上限は20MBです。

保存処理はIndexedDBの読み書きトランザクションで行うため、複数タブの同時登録で更新を失わないようにしています。テンプレートは全食品を検証してから一括保存し、途中だけ成功させません。

## iPhoneのホーム画面に追加

1. Safariで https://pfc-bay.vercel.app を開きます。
2. 既存の記録がある場合は「設定」から先にバックアップを書き出します。
3. Safariの共有ボタン →「ホーム画面に追加」を選択。「Webアプリとして開く」が表示される場合はオンにして追加します。
4. ホーム画面の「PFC Tracker」アイコンから起動します。必要なら先ほどのバックアップを読み込みます。
5. 初回はネットに接続したまま「設定」の **オフライン準備完了** を確認します。その後は機内モードでも再起動・画面移動・記録できます。

Safariとホーム画面版では保存領域が分かれる場合があります。ホーム画面版で記録が空でも、元のSafariのデータを削除せず、バックアップで移してください。同じ手順でホーム画面版も端末連携でき、スマホ・PCと自動同期します。

ホーム画面版ではブラウザのアドレスバーがない独立した画面で開きます。Manifestのid/scope、192/512pxアイコン、maskable・Apple Touch Icon、Apple/標準のWebアプリ用meta、viewport-fit=cover、ノッチ/ホームバーの安全領域、16px以上のモバイル入力欄を用意しています。画面拡大そのものは制限しません。

**オフライン:** 本番ビルド時にアプリの全画面と必要なJS/CSS/アイコンの保存リストを生成します。Service Workerは公開されたアプリ本体だけを保存し、認証・API・RSCレスポンスや食事データをキャッシュしません。食事は従来と同じIndexedDBに保存します。オフライン時の画面移動は保存済みのHTMLを使います。初回の準備が終わる前や、iOSが保存領域を削除した場合は、接続して再準備が必要です。端末の空き容量やiOSの保存方針まではアプリで保証できないため、定期バックアップを推奨します。

**更新:** 新版を取得しても、開いているフォームを突然再読み込みしません。「更新があります」が出たら「設定 → 更新して再起動」を押します。更新でIndexedDBの記録を消すことはありません。準備に失敗した新版で現在のアプリを置き換えない構成です。

iPhone実機での最終チェック項目:

- [ ] Safariから追加し、ホーム画面のアイコンからアドレスバーなしで起動
- [ ] オフライン準備完了後、機内モードで終了・再起動・食品/履歴/設定への移動
- [ ] 画面下のホームバーとナビが重ならず、食品の入力・保存ができる
- [ ] 「ファイルに保存・共有」でiCloud Drive等へ保存し、ファイルから復元できる
- [ ] Safariでの既存記録をバックアップ経由でホーム画面版へ移せる

このクラウド環境ではWebKitのダウンロードがネットワーク制限で拒否されたため、Safari実機検証は未実施です。ChromiumのiPhone相当設定でオフライン起動・表示・共有APIの呼び出し・更新後の記録保持を検証します。共有シートとホーム画面モードのテストはブラウザAPIを模擬し、実際のiOSインストール/共有操作を保証するものではありません。

## ローカル開発

Node.js 22.13以上（24.19で検証）、npmを使用します。端末内保存だけなら外部サービスは不要です。自動同期を使う場合は、`.env.example` の2つのSupabase公開設定を追加します。メール設定は不要です。

```bash
npm ci
npm run dev
```

開発サーバーではService Workerを新規登録しません。PWAの確認には本番ビルドを使用してください。

本番ビルド:

```bash
npm run build
npm start
```

`npm run build` はNext.jsのビルド後に `scripts/build-pwa.mjs` を実行し、ビルド単位の `public/sw.js` を生成します。生成物はGit除外です。修正する場合は `scripts/sw-template.js` を編集してください。

Next.js App Router / React / strict TypeScript / Tailwind CSS / shadcn/ui形式のButton / Lucide / Zod / decimal.jsを使用。ロックファイルで依存関係を固定しています。ブラウザ保存はネイティブIndexedDBを使用します。

## Vercel

GitHubの `YosukeMasonHashimoto/PFC` の `main` に接続します。Application PresetはNext.js、Root Directoryは `./`、Build Commandは自動設定を使用します。

自動同期には `NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` が必要です。以前Vercelに登録した値を使用できます。`APP_URL` は不要です。`SUPABASE_ACCESS_TOKEN` やservice_roleキーはVercelへ登録しないでください。同期設定前はSupabaseにアクセスせず、端末保存だけで使えます。

GitHubへpushした後、Vercelの最新Production DeploymentがReadyになったら公開ページを再読み込みしてください。古い `/login` のブックマークからもホームへ移動します。

## 旧クラウド版について

Supabaseに適用済みのDBやRLSは、今回の変更では削除・公開しません。**既存のクラウド記録を端末内へ自動移行する機能はありません。** 必要な既存データがある場合は別途移行が必要です。

メールログインと旧クラウドAPIは停止したままです。旧 `/api/data` はHTTP 410を返します。新しい同期はブラウザの匿名端末セッションと、暗号化ドキュメント専用のRPCを使用します。旧食品・食事テーブルは公開せず、旧データを勝手に移動しません。

## 今日の目標まで、あとどれくらい？

全画面に当日の（履歴では選択日の）P/F/C・カロリーの不足量・超過を表示します。カードはスクロールに追従しません。登録食品の現在の栄養値と食事の保存済みスナップショットから、追加する食品とグラム数を提案します。提案は表示のみで、食事の登録は通常の記録フォームから行います。

提案量は、選択日までの食品ごとの直近30記録を参照し、頻度・直近順で選んだ最大3種類の実測量だけを使用します。1記録を1食分とし、間食を1日分に合算しません。未記録食品は候補にせず、204g/201gのような未記録の重量や、1食分を勝手に倍増した量を生成しません。最大5品目の異なる食品を組み合わせて不足を補います。実績の候補だけでは不足する場合は、残量を表示したままにします。カロリーは入力値を使い4/9/4で上書きしません。目標超過は計算の誤差として隠さず表示します。近似探索であり、栄養目標の完全一致を保証しません。

フォームから取り除いた項目は既存バックアップとの互換性のため内部形式には保持し、編集時も既存の値・ポーションを消しません。新規食品は手動入力として保存します。過去の食事の栄養値は変更しません。

今回のフォーム簡略化・食事目安追加後、ユニット/DBテスト45件・本番ブラウザ9シナリオ・Lint・型検査・本番ビルドが成功しました。削除したフォーム項目が表示されないこと、候補分量から記録を開けること、保存後の残量再計算とスクロール中の常設表示を確認しています。

## スマホ・PCの自動同期

最初に一度だけ連携します。

1. 既存記録のある端末で「設定 → スマホ・PCの自動同期 → この端末から同期を開始」。
2. 「別の端末を連携する → 連携リンクをコピー」を押し、自分のもう一方の端末で開きます。
3. もう一方の端末で「この端末を連携」を押します。リンクではなく同期コードの直接入力も可能です。

以降は、記録変更後・画面に戻ったとき・接続が戻ったとき、および前面表示中は約15秒ごとに同期します。iOSがアプリを休止している間のバックグラウンド常時同期は保証しません。変更がないときはリビジョンだけを確認し、大きな記録全体を再転送しません。オフライン中も保存し、再接続時に統合します。初回連携だけは通信が必要です。

**初回の既存データ:** 他方に存在しないIDの記録を追加し、同じIDや同じ目標開始日は既存のクラウド版を優先します。別々に作成した同名食品は、誤った同一視を防ぐため別食品として残る場合があります。連携前のこの端末の記録を退避し、「連携前の記録を書き出す」から回収できます。通常のバックアップも残してください。

**同時編集:** 同期済みの基準データ・現在の端末データ・最新クラウドデータの3方向で行単位に統合します。異なる記録の追加・変更は両方保持します。同じ記録を同時に編集した場合は、後に同期された端末の変更を優先します。削除した食品を参照する食事は栄養スナップショットを保持して参照をnullにします。サーバーのリビジョン比較により、古いスナップショットによる無条件上書きを防ぎます。通信中に追加された端末の記録も同期応答で消しません。

**プライバシー:** Supabase匿名認証で端末セッションを自動生成しますが、メール・パスワードの入力は不要です。AES-256-GCMで端末側で暗号化し、復号鍵は同期コードに含めます。Supabaseには暗号文・リビジョン・端末のアクセス権だけを保存します。同期コード/リンクは記録へのアクセス鍵なので第三者へ共有しないでください。リンクの秘密部分はURLフラグメントを使い、アプリが読み取った後に履歴から除去します。シークレットをサーバーへ送る代わりに別用途のハッシュ証明を用いて連携します。

「この端末の同期を停止」は自動同期だけを止め、記録を端末に残します。他端末や、すでにコピーされたコードの権限を取り消す操作ではありません。全端末の保存領域と同期コードを失うと暗号化データを復号できません。通常のJSONバックアップはデータのみで、同期コードは含みません。同期上限は暗号化前8MBです。超えた場合も端末内データは残し、エラーを表示します。

### 同期サービスのセットアップ

この環境の既存Supabaseでは適用済みです。新しいプロジェクトでは以下を行います。

- Auth設定で匿名サインイン（Anonymous sign-ins）を有効化。匿名セッションのレート制限は維持してください。
- `supabase/migrations/202610270002_device_sync.sql` を一度適用。旧食品テーブルは新同期に不要です。
- Vercelに2つの `NEXT_PUBLIC_SUPABASE_*` を設定し、HTTPSで使用します。サーバー秘密鍵は不要です。

`sync_workspaces` と `sync_members` はRLSを有効化し、未連携端末の読み取りや直接書き込みを拒否します。作成・連携・リビジョン付き更新は認証済みRPCだけに許可します。復号鍵はDBに保存しません。匿名セッションの新規作成にはSupabase側の回数制限があり、プロジェクトの利用上限・容量・通信量も通常どおり適用されます。

### 同期の検証

ブラウザE2Eはテスト専用のSupabase HTTPアダプターに接続し、本番記録・認証情報を使わず、独立したブラウザ間で双方向自動同期・オフライン変更の統合・再読み込み後の保持を検証します。`npm run test:e2e` はテスト用公開設定でビルドするため、手動の本番起動前には通常の `npm run build` を実行してください。DBテストでは実PostgreSQLでRLS、誤ったコードの拒否、競合更新の拒否、未変更時の暗号文転送省略を確認します。

実Supabaseでも一時的な検証専用の匿名2端末を作成し、連携前の読み取り拒否・誤コード拒否・暗号文の共有/復号・競合制御を確認し、テスト用端末とワークスペースを削除しました。ユーザーの既存記録は操作していません。iPhone実機・Vercelの最新デプロイ反映は別途確認が必要です。

## 実績分量・端末同期の検証結果

Lint・型検査・ユニット/実PostgreSQLテスト60件・本番ブラウザ10シナリオ・通常設定での本番ビルドが成功しました。実際に記録した量だけを提案すること、スーパー大麦20g・たまご50g等を勝手に204g/201gへ増やさないことを検証しています。別ブラウザ間の自動同期はテスト用HTTPアダプターで、アクセス制御・暗号文の共有・リビジョン競合・未変更データの転送省略は実Supabaseでも確認しました。実サービスの検証専用セッションと記録は削除済みです。

食品登録では「基準の分量 (g)」を自由に入力し、その分量あたりのP/F/C・カロリーを登録できます。保存時に100gあたりへ換算し、一覧・編集時は換算後の値を表示します。既存食品・バックアップ・食事記録の形式は維持します。

### 制限のある環境でのブラウザ確認

Turbopackのローカルポート作成が制限される環境では、ローカル通信の権限を有効にして次を実行します。Webpackで本番ビルドし、テスト専用のSupabaseアダプターで検証するため、本番データにはアクセスしません。

```sh
PFC_E2E_WEBPACK=1 PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium npm run test:e2e
```

Chromiumのパスは環境に合わせて指定してください。Playwrightのブラウザを利用する場合は `PLAYWRIGHT_CHROMIUM_EXECUTABLE` を省略できます。食品の任意分量入力・再読込後の保持・編集時の換算値・食事記録の栄養計算・食事目安の表示とスクロールを検証し、`test-results/` にモバイル・デスクトップのスクリーンショットを保存します。
